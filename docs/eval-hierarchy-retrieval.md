# Hierarchy-first retrieval: first measurement

Generated by `scripts/hierarchy-retrieval-bench.ts` (data: `docs/eval-hierarchy-retrieval.json`, questions: `docs/eval-hierarchy-retrieval-gold.json`). Run on this repository at `10f82b2` plus the uncommitted prototype. Offline and deterministic: no model was called.

**The question.** If the context sent to a model is chosen from the concept hierarchy first, can it be smaller without losing what the answer needs?

**How it was measured.** 17 questions about this repository (8 using the code's own words, 9 paraphrased), 27 files a good answer needs. Each method ranks functions, the best-ranked are fitted into a token budget with the same bundle builder, and we count how many needed files are inside. "Tokens" means what a model is actually sent (the bundle after the provider's projection: entities, relationships, behavioural facts), not the raw bundle.

## Results

Gold-file recall at each budget (95% Wilson interval):

| sent-token budget | current retrieval (baseline) | flat search over hierarchy metadata | two-stage (domain groups first) |
|---|---|---|---|
| 500 | 30% [16–48] | 4% [1–18] | 4% [1–18] |
| 1,000 | 48% [31–66] | 7% [2–23] | 11% [4–28] |
| 2,000 | 56% [37–72] | 15% [6–32] | 22% [11–41] |
| 4,000 | 70% [52–84] | 30% [16–48] | 30% [16–48] |
| 8,000 | 78% [59–89] | 44% [28–63] | 52% [34–69] |
| 16,000 | 78% [59–89] | 59% [41–75] | 59% [41–75] |

At 2,000 sent tokens, by question kind: named questions baseline 91% vs 36% / 36%; paraphrased questions baseline 31% vs 0% / 13%.

## What this says

1. **The hierarchy-first prototype did not beat the ranking the system already has.** The gap to flat search is outside the intervals from 1,000 to 4,000 tokens (at 500 they overlap slightly); against two-stage the intervals touch at some budgets (2,000 and 8,000). It did not help on paraphrased questions, the case it was meant for.
2. **Grouping added nothing measurable over flat search.** By construction a domain group's word comes from its members' own identifiers, which flat search already reads. Differences between the two are within noise.
3. **The hierarchy's names did not help here, because this run used mechanical names** (`<shape> in <function>`), which carry no domain vocabulary. Model-written names are searchable too and could change this. That is untested.

## The finding that matters more: the token budget is measured on the wrong thing

| | tokens | gold-file recall |
|---|---|---|
| raw bundle, unbudgeted (mean) | 778,510 | — |
| what a model is sent for that bundle (mean) | 8,468 | 78% (12/17 questions fully covered) |
| what the service does today (budget 60,000 raw) | median 55,679 raw, **560 sent** | **33%** (5/17 fully covered) |

- A bundle's raw size is dominated by facts and evidence a model is never sent (for example dozens of `defect.semantic-event` facts per function). The model provider sends only entities, relationships and behavioural facts.
- The service cuts to its budget by dropping entities, but the facts attached to the entities that remain stay in the raw estimate. So it drops almost everything to get under the number: a median of 560 tokens sent, and recall falls from 78% to 33%.
- It still does not get under the limit in every case: **3 of 17 questions stay above the gateway's 200,000-token limit**, which rejects the request with `BUDGET_EXCEEDED`.
- At the same sent size the existing ranking does much better: 56% recall at 2,000 sent tokens, 70% at 4,000, 78% at about 7,500.

**Suggested next step (not done here): budget on the sent size, not the raw size.** That is a small change to where the budget is measured, it should raise recall and remove the false limit errors, and it needs no hierarchy.

## Limits of this measurement

- The 17 questions and their gold files were written by the same assistant that wrote the prototype, not by an independent labeller. Replace the gold file with your own questions to measure your repository.
- Seventeen questions: every interval is wide.
- File-level recall only. It says the needed files are inside the context, not that a model answers well from it. Answer quality needs a judge (a model or a person) and was not measured.
- Baseline is `retrieveForQuestion` with default options. The chat path may add concept cards, pins and semantic matches, so today's real behaviour may differ.
- The sent-token projection is copied from `packages/model/src/ollama.ts` (`compact`), not imported; keep the two in step.
- One repository, one language mix. A repository with fewer defect facts per file would show a smaller raw/sent gap.
